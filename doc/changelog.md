# Change log

Part of the [PR3 documentation](README.md). Newest first; each version records what changed in the design and why.

## v1.22 (27 October 2026) - voice notes always send on a pause

1. **Send on pause, always.** A tapped voice note is sent once you stop talking for two seconds, or at a second tap; the **Send on pause** switch is gone, leaving one setting fewer. A held note is still sent when you let go.
2. **A shorter header.** The version, platform and model sit beside the name, and the header's buttons share one row below, so the header takes two lines on a phone instead of four.

## v1.21 (26 October 2026) - voice-note language and the benchmark report

1. **Voice-note language.** A chip beside the talk button picks the language of voice notes and spoken replies: *Auto* follows the system, as before, and the list holds only languages this device recognizes on the device, so picking one never sends audio anywhere. Apple devices list the locales whose on-device model is installed; Android 13 and later add those it downloads on first use, and earlier Android versions offer the system language only. Changing it reopens both engines, ends a voice note or reply in progress, and is remembered.
2. **Benchmark report** (`bench/agentdojo/report.py`). The tables of [Sec. 8.6](benchmarks.md#86-results-so-far) are generated from the result files, and refuse to mix approver or harness versions. Successful attacks that no runtime can stop are counted apart, from AgentDojo's own task definitions: text-only attacks, whose goal is something the model says, and approver gaps, where the user's own task needs a call to the same place.

## v1.20 (26 October 2026) - CI on every platform

The CI matrix of [Sec. 12](quality-gates.md#12-build-cicd--quality-gates), begun: the workspace is built and tested on macOS, Linux and Windows, the app's Rust and Swift code is built for the iOS simulator, and the Android APK with its Kotlin plugins is built for arm64. To keep runs short, formatting, clippy's lints, the trusted-side rule and the `no_std` builds run once, on macOS, since they do not depend on the platform, while Linux and Windows build and test with compiler warnings as errors; every job installs only the targets it uses, caches per platform, builds without debug info, and a new push to a pull request cancels the run it replaces. Text files are checked out with LF endings everywhere (`.gitattributes`), so scripts run under bash on Windows.

The first run found three things, now fixed. On Windows, `swift-rs`, which builds the vault's and speech's Swift halves, could not link: it is now a build dependency only on a Mac, the only machine that builds Swift (Cargo matches a build dependency's platform against the building machine); the same change corrected the Swift folder those build scripts watch, which the singular-folder rename had missed, so a Mac no longer rebuilds Swift every time. cargo-fuzz defaulted to the target its prebuilt binary was built for, musl, where the sanitizer does not run; `script/fuzz.sh` now names the machine's own target. And the audit found five advisories: `time`, `tokio` and `quick-xml` (through Tauri's `plist`) took in-range updates, and `crypto-bigint`'s timing variability in constant-time operations, used by the P-256 signatures that approve actions, needed `p256` 0.14. What remains are seven warnings about unmaintained crates in Tauri's Linux dependencies.

## v1.19 (25 October 2026) - fuzzing and Miri

M1-E6's hardening for the parsers of untrusted input ([Sec. 12](quality-gates.md#12-build-cicd--quality-gates)), on a nightly pinned apart from product builds (`fuzz/rust-toolchain.toml`).

1. **Five fuzz targets** (`fuzz/`, cargo-fuzz, `script/fuzz.sh`). Each checks a guarantee, not only the absence of panics: the core's agent loop under arbitrary model replies, calls and tool results runs only registered tools with arguments that fit their schema, and hands a consequential tool to the host only as a proposal; the trusted gate under forged signatures, altered receipts and arbitrary audit logs issues a capability only for a receipt the device key signed exactly as approved, once per approval, and redeems each capability once; phone↔computer messages decode from arbitrary bytes and re-encode the same way; the model-output path gives the same answer and calls whether the tokens split a tag or not; and memory search cannot be broken by the search index's query syntax. Dictionaries of each format's tokens and seed outputs take the fuzzer past simple input.
2. **Results.** About nine million inputs, with no crash and no broken guarantee. One check was wrong, not the code: where the model writes tag fragments around a block (`<to<tool_call>…</tool_call>ol_call>`), removing the block joins them into a tag in the visible answer. Calls come only from complete blocks and the answer is never parsed for calls, so that text stays text; the target now checks the property that matters, independence from how tokens split.
3. **Miri** runs `pr3-core`'s tests, the trusted side included, with four cases per property test because Miri interprets every instruction: all 45 pass with no undefined behaviour, in about an hour.
4. **CI** gains both: a minute of fuzzing per target on every change, keeping any failing input as an artifact, and Miri on `pr3-core` on pushes to `main` and weekly, since it takes about an hour. The whole workflow also runs weekly, so new advisories reach the audit.

## v1.18 (25 October 2026) - the memory panel

The rest of M2-E7's "conversation → memory proposals" ([Sec. 4.4](architecture.md#44-memory-and-knowledge-architecture)): what the model proposes, the user reviews.

1. **Memory panel.** A **Memory** button shows what PR3 remembers in two groups. *To review* holds the model's proposals, each with the words it came from ("From what you said on 21/10: …") and Confirm, Edit and Forget. *Confirmed* holds the user's own entries, confirmations and corrections. The user can also add a memory directly. Editing stores a correction that replaces the memory, so the earlier version is no longer recalled; forgetting takes a second tap and erases the memory, its earlier versions and the words it came from. The panel refreshes after each turn, so a new proposal appears while it is open.
2. **`pr3-memory`.** The store interface gains `confirm`: a live proposal becomes confirmed and fully trusted, keeping its source. Confirming, correcting, adding and forgetting stay out of the model's reach; they are app commands the user triggers, never tools.

## v1.17 (22 October 2026) - voice notes

Spike step 7 ([Sec. 11](roadmap.md#11-delivery-roadmap-epics--issues), M2-E7): push-to-talk voice notes and spoken replies, on the device only ([Sec. 4.3](architecture.md#43-inference-strategy)).

1. **`pr3-speech`.** A `Recognizer` and a `Voice` trait, so speech engines swap the way models do. On Apple devices the Speech framework, with on-device recognition required: where a language has no on-device model, PR3 tries the same language in its main region (English (UAE) falls back to English (US)) and otherwise offers no voice input rather than send audio to a server. Replies are spoken by the best installed system voice for that language, never a novelty voice or the user's Personal Voice. The Swift half is linked with swift-rs, as `pr3-vault`'s is, and called from the crate's one audited `unsafe` module; no callback crosses that boundary: a Rust thread reads each session's events.
2. **Android.** A Kotlin plugin in the app uses only the on-device `SpeechRecognizer` (Android 12 and later) and a `TextToSpeech` voice that needs no network. Where the language's on-device model is missing, Android 13 and later download it on PR3's request; only the model is downloaded. The recognizer ends a segment after a pause; while the button is still held, PR3 starts another and the transcript grows.
3. **App.** Hold the talk button, speak and let go; or tap it, speak and tap again. With **Send on pause** (on by default, beside **Speak replies**), a tapped note is sent once you stop talking for two seconds. Either way no Send button is needed. The transcript appears as you speak and is sent like typed text, so memories it leads to are proposals with your words as their source ([Sec. 4.4](architecture.md#44-memory-and-knowledge-architecture)). **Speak replies** reads each final reply aloud, with Markdown read as plain sentences; it is off by default and remembered. Starting a voice note stops a reply being spoken, and Send during a voice note ends it. If the recognizer fails mid-note, the app says so at once; a note that hears nothing for 30 seconds ends by itself, so the microphone never stays open unattended. The microphone and speech recognition prompts come with the first voice note. No audio is kept.

Checked with a real voice on the Android emulator (API 36): live transcript, sending on release and on a pause, spoken replies, including the first one after the voice engine starts. On the Mac the voice and the language fallback were checked through `pr3-speech`. The iOS 27 simulator shows both permission prompts and opens the microphone, but its own on-device speech model is installed damaged, so transcription there waits for a Mac or an iPhone.

This also delivers part of M4-E6 early: voice notes on iOS and spoken replies on iOS and Android. Still to come: whisper.cpp where no on-device recognizer exists (desktop Linux and Windows, older Android), choosing the language in settings, and low-latency spoken conversation through the node.

## v1.15 (21 October 2026) - the computer as the user's node

Spike step 6 ([Sec. 11](roadmap.md#11-delivery-roadmap-epics--issues)): pairing and handoff between a phone and the user's own computer.

1. **Pairing** (M2-E3, `pr3-hybrid`). The computer shows a six-digit code, valid for one attempt within two minutes. Phone and computer run SPAKE2 on it, so an eavesdropper cannot test guesses offline and an active attacker gets one guess per code. The key it yields authenticates a Noise `XXpsk3` handshake in which each side learns the other's long-term X25519 key. Forgetting a phone on the computer revokes it.
2. **Sessions.** Every connection is a Noise `IK` handshake between paired keys - mutually authenticated, forward-secret, and refused for any key the computer has not paired with - carrying `pr3-protocol` v0 messages as CBOR (a new crate whose types are `no_std`). Messages are size-bounded, encrypted and in order, and nothing replays into another session. Cancelling stops the computer's model at its next token without stopping its engine.
3. **Handoff, spike-sized** (M2-E2). The computer lends its model; the phone keeps the conversation, memory, tools and the trusted side. A paired phone sends each model call to the computer, answers with its own model when the computer cannot be reached, and says which answered in its header. A node's model can propose an action, but the phone validates the proposal against its own address book, shows its own card and signs with its own key - checked with Qwen3.8-27B on a Mac proposing an email that the iPhone simulator's card then showed and declined. Delegating whole tasks and proactive jobs (M2-E4, M5-E4), discovery on the local network and the TLA+ model of the handoff protocol ([Sec. 12](quality-gates.md#12-build-cicd--quality-gates)) come later.
4. **Defaults.** The computer listens on 127.0.0.1 only, which reaches the iOS simulator and, as 10.0.2.2, the Android emulator; phones on the network need `listen = "0.0.0.0:7313"` under `[node]`.

## v1.14 (21 October 2026) - approval keys in platform key storage

1. **Apple devices.** The approval key is a P-256 key in the Secure Enclave whose access policy requires Face ID, Touch ID or the device passcode for every signature. CryptoKit wraps it so that only this device's Secure Enclave can use it, and the wrapped form is kept in the app's data folder; no keychain entitlement is needed, so unsigned development builds on a Mac use the Secure Enclave too. The system's prompt names what is approved ("send the email “Lunch” to Alex Rivera"); the OS draws it, outside the webview. The iOS simulator cannot create such keys, so there a software key signs after the same LocalAuthentication check, and the vault labels itself accordingly.
2. **Android.** A P-256 key in the Android Keystore (StrongBox when the phone has one) that requires user authentication for each use: BiometricPrompt with a CryptoObject unlocks exactly one signature, with a strong biometric or, from Android 11, the screen lock. Without a secure screen lock the key cannot be created, so actions stay off and the log says why.
3. **`pr3-vault`.** `sign` now receives the reason the prompt shows and can answer "cancelled", which ends the request like a decline. The Swift half (`swift/`) is linked with swift-rs, as Tauri links its own, and called from the crate's one audited `unsafe` module; Android's half is a Kotlin plugin in the app, because BiometricPrompt needs the app's activity. A software key from earlier builds is deleted once the platform key exists.

The passcode or screen lock is accepted as a fallback, as the platforms' own payment confirmations accept it; requiring biometrics only is one flag on each platform.

## v1.13 (21 October 2026) - the trusted side for one action

Spike step 5 ([Sec. 11](roadmap.md#11-delivery-roadmap-epics--issues)): sending an email through a sandbox connector, by the path [Sec. 4.6](architecture.md#46-structured-intent-and-execution-sequence) describes.

1. **Trusted side in `pr3-core`** (`trusted`, `no_std`, M1-E7). The intent validator checks the runtime's envelope (nonce, time, freshness, a replay window), refuses fields the operation does not define, and resolves recipients by name from the user's address book, so the model never types an address; a subject cannot break a line to add mail headers, and no text may carry the invisible characters that reorder it on screen. A deterministic policy applies a kill switch, a recipient limit, a daily limit and one approval at a time, and every email needs approval. Approval receipts are verified with P-256 ECDSA, the curve Secure Enclave and Android Keystore sign with, and exchanged for one-use capabilities that expire in 30 seconds. The audit log is a SHA-256 hash chain that keeps addresses and hashes, not message text. Proptest checks the [Sec. 12](quality-gates.md#12-build-cicd--quality-gates) properties: no capability without a receipt that matches the request exactly and is signed by the device key, nothing authorized after expiry or twice, and any rewrite of the log detected. A CI script keeps the trusted modules free of agent-side imports.
2. **Agent loop.** Calls to consequential tools reach the host as `Action::Propose` instead of being refused; the host answers with the outcome - sent, declined, denied or expired - like any tool result.
3. **`pr3-vault`** signs approved receipts. For now the key is a file in the app's private, backup-excluded folder (`dev` tier, [Sec. 7.3](security.md#73-trust-tiers---dev-protected-secure)); Secure Enclave and Android Keystore, with a biometric prompt, replace it behind the same trait.
4. **App.** A confirmation card shows the recipients' real addresses, the subject and the exact text, from the validated intent, with Send, Decline and a two-minute expiry. The sandbox outbox delivers once per capability. `audit.jsonl` is verified at every start, and a log that does not verify turns actions off. Contacts and limits live under `[actions]` in `config/pr3.toml`.

Not yet: biometric approval with keys in platform storage (v1.14), signed audit checkpoints, connector manifests (M5-E1), and confirmation on the phone for actions prepared on the desktop (step 6).

## v1.12 (21 October 2026) - hardening after the first review

A whole-project review of spike steps 1–4 found no design problems but several gaps between what the code promised and what it did. All were fixed before step 5.

1. **Security.** Message text can no longer forge chat-control tokens: prompts are tokenized in pieces, with only the template's own turn markers as control tokens, and model output is printed without them ([ADR-003](adr/003-llamacpp-binding.md)). Memory arguments and notes are kept to one line, so a memory cannot pose as the user's words or as a "confirmed" line. Tool schemas must use the subset the core enforces (`enum` included); anything else is refused at registration. The webview may only listen for events.
2. **Privacy.** Forgetting erases a memory from the search index too (FTS5 `secure-delete`, with a migration that purges words older builds left behind), along with its principal and, once unused, the user's source words. Traces are off unless `config/pr3.toml` turns them on, and they rotate. App data is excluded from cloud backups and device transfer on Android and from iCloud and computer backups on iOS, as the `device_only` consent scope says.
3. **Failure paths.** A new `Input::Abort` lets the host end a turn after any failure, so one crash no longer locks the session. History and the prompt window are trimmed by whole exchanges, never splitting a tool call from its result or dropping the current question. Refused tool calls and calls over the per-message limit are kept in outline only. The loop guard keeps identical-call detection and a per-turn budget; its name-only ping-pong check stopped legitimate turns. The engine can be stopped mid-answer, and quitting waits for it and for a model still loading before the process exits. Computers with less memory fall back to a smaller model.
4. **Build.** The Android dot-product flag moved to `script/build-android.sh` (it had also changed the Apple builds), the toolchain is pinned in `rust-toolchain.toml` with an honest minimum version (1.90), and CI checks formatting, lints, tests, the `no_std` builds and dependency advisories ([Sec. 12](quality-gates.md#12-build-cicd--quality-gates)).

## v1.11 (21 October 2026) - memory with provenance

1. **`pr3-memory` and `pr3-memory-sqlite`** ([Sec. 4.4](architecture.md#44-memory-and-knowledge-architecture), M1-E5): every memory carries the [Sec. 4.4](architecture.md#44-memory-and-knowledge-architecture) provenance - source, principal, created and valid times, confidence, privacy class, consent scope and retention. The model can only propose memories, each traced to the words the user said that turn; the user's own entries and corrections are confirmed and supersede proposals. SQLite (bundled, so iOS and Android run the same engine) with FTS5 search ranked by bm25, versioned migrations, and forgetting that erases a memory's text, its earlier versions and its source words, leaving a tombstone; deleted pages are overwritten.
2. **Memory reaches the model two ways:** `remember` and `recall` tools, and a lookup the host runs for every message, passed to the core as notes and shown to the model ahead of the user's words ([Sec. 3](overview.md#3-guiding-engineering-principles), deterministic first). Traces record it as an OpenJarvis `retrieve` step. With the lookup, Qwen3.5-2B recalled a fact from an earlier conversation in 8 of 8 runs, against about half when it had to call `recall` itself.
3. **Not yet:** forgetting and correcting memories from the app (user actions, built with the trusted side in spike step 5), encryption at rest (M3), and extracting memories the user did not ask PR3 to keep.

## v1.10 (21 October 2026) - prompt cache reuse

1. **`pr3-llamacpp` keeps one llama.cpp context per engine and reuses it** ([ADR-003](adr/003-llamacpp-binding.md)): each call processes only the part of its prompt the context has not already seen, so a tool round and the next turn skip the system prompt, the tool list and the conversation so far. Hybrid models (Qwen3.5 and later) rewind through checkpoints of their recurrent state. On the CPU, as phones run it, Qwen3.5-4B answers after a tool call in 0.6 s instead of 4.5 s.

## v1.9 (20 October 2026) - a model per device class

1. **Default models move to the Qwen3.5 generation** ([Sec. 4.3](architecture.md#43-inference-strategy)): Qwen3.8-27B on desktops and the node; Qwen3.5-4B on phones with 8 GB or more and Qwen3.5-2B below that. Qwen3.8 has no small sizes, so phones stay on Qwen3.5. Both generations share one chat template and tool-call format. Qwen3-0.6B remains as a tiny test and fallback model.
2. **`config/pr3.toml` chooses the model per device class** and pins every model to a repository revision and SHA-256; `script/fetch-model.sh` downloads and verifies them. A copy in the app's data folder overrides the built-in file.
3. **Android builds llama.cpp's CPU kernels for ARMv8.2 with dot products** ([ADR-003](adr/003-llamacpp-binding.md)), which makes 4-bit models about 2.5 times faster than the bindings' ARMv8.0 default.
4. **`pr3-llamacpp` reads the prompt format from the model's own chat template** ([ADR-003](adr/003-llamacpp-binding.md)): Hermes-style JSON tool calls for Qwen3, XML calls for Qwen3.5 and later, with the prompt rendered exactly as each template renders it. `ChatMessage` now carries an assistant turn's tool calls, so the engine replays them in the model's format.

## v1.4 (19 October 2026) - review corrections

v1.4 corrects security-design gaps, build claims that would not hold, and gate definitions found in review. Direction and scope are unchanged.

1. **Intent envelope** ([Sec. 4.1](architecture.md#41-functional-modules), [Sec. 4.6](architecture.md#46-structured-intent-and-execution-sequence)): identity, nonce and timestamp are stamped by the runtime from the session binding and host clock/entropy; the model supplies only enumerated or bounded values, and any identity or replay field in its output is rejected.
2. **Execution credential location** ([Sec. 4.6](architecture.md#46-structured-intent-and-execution-sequence), [Sec. 6.3](deployment.md#63-private-hybrid-mobile--desktop), [Sec. 11](roadmap.md#11-delivery-roadmap-epics--issues) M5, [Sec. 13](risks-and-governance.md#13-risks--mitigations)): for live providers the credential and execution adapter stay on the phone; the node holds neither an approval key nor a provider credential, otherwise "prepare but not approve" does not hold.
3. **Push relay** ([Sec. 4](architecture.md#4-reference-architecture), [Sec. 6.3](deployment.md#63-private-hybrid-mobile--desktop), [Sec. 7.1](security.md#71-threat-model), [Sec. 11](roadmap.md#11-delivery-roadmap-epics--issues) M2-E5): APNs/FCM require a publisher-operated relay (or UnifiedPush); it carries sealed wake-ups only and is in the threat model.
4. **`pr3-ffi` full and core builds** ([Sec. 4.2](architecture.md#42-rust-workspace-host-api-c-abi-and-protocol-client), [Sec. 6.5](deployment.md#65-what-ships-where), [RFC-001](rfc/001-console-cognition-tiers.md)): `std` + UniFFI + adapters with unwind, and `no_std` core with abort, as separate profiles; Cargo cannot set `panic` per package.
5. **Panic-site allowlist** replaces "no panic symbols", which `alloc` makes unachievable ([Sec. 4.2](architecture.md#42-rust-workspace-host-api-c-abi-and-protocol-client), [Sec. 7.2](security.md#72-required-controls), [Sec. 8.5](benchmarks.md#85-proposed-acceptance-gates-targets-not-measured-results), [Sec. 12](quality-gates.md#12-build-cicd--quality-gates)).

## v1.3 (19 October 2026) - lineage from the AI OS plan

v1.3 folds in the reusable parts of an earlier plan for a pure AI OS, a secure operating platform on a verified microkernel with AOSP and Debian guests. Its own pivot clause (Sec. 31.5 there) anticipated the embeddable-runtime shape of v1.2, so v1.3 is the execution of that clause rather than a change of direction. The OS, shells, VMM, hardware, team, budget and fundraising content of the AI OS plan is **not** carried over; [the lineage](lineage.md) maps every section to reused / adapted / dropped.

1. **Trust-boundary schemas** ([Sec. 4.6](architecture.md#46-structured-intent-and-execution-sequence) new): structured intent, validator rules and the propose → validate → policy → confirm → scoped capability → execute → audit sequence; capability and approval-receipt schema ([Sec. 7.2](security.md#72-required-controls)); hash-chained, signed-checkpoint audit ([Sec. 4.4](architecture.md#44-memory-and-knowledge-architecture)).
2. **Security invariants and expanded threat model** ([Sec. 7.1](security.md#71-threat-model)), with "model ≠ authority", the propose/dispose split and "stay useful when the model is gone" promoted to engineering principles ([Sec. 3](overview.md#3-guiding-engineering-principles)).
3. **Trust tiers** ([Sec. 7.3](security.md#73-trust-tiers---dev-protected-secure) new): `dev` → `protected` → `secure`. The phone is the trusted confirmation device for node-prepared actions ([Sec. 6.3](deployment.md#63-private-hybrid-mobile--desktop)). A verified-microkernel tier is one the same `no_std` trusted-side modules can target later, not a deliverable ([ADR-002](adr/002-trust-architecture.md), [the ADRs](adr)).
4. **Identity model** ([Sec. 4.1](architecture.md#41-functional-modules), [Sec. 6.3](deployment.md#63-private-hybrid-mobile--desktop)): device, user, agent and protocol-host identities with registered keys and revocation; grants, approvals and capabilities bind to identity.
5. **Memory data separation and disclosure checklist** ([Sec. 4.3](architecture.md#43-inference-strategy), [Sec. 4.4](architecture.md#44-memory-and-knowledge-architecture)): canonical / derived / ephemeral; derived indexes rebuildable; per-backend disclosure evaluation recorded in the trace.
6. **Connector and plugin model** ([Sec. 4.7](architecture.md#47-connector-and-plugin-model) new): integration hierarchy and signed manifest; never screen automation for high-risk operations.
7. **Verification** ([Sec. 12](quality-gates.md#12-build-cicd--quality-gates)): narrow formal methods - Kani on the policy, capability and approval state machines; a TLA+ model of the handoff/sync protocol checked under fault injection; Proptest on the capability lifecycle - plus required test layers and release channels.
8. **Roadmap and gates** ([Sec. 11](roadmap.md#11-delivery-roadmap-epics--issues), [Sec. 14](roadmap.md#14-success-metrics--gono-go-gates)): trusted-side modules and `pr3-vault` land in M1; phone-side confirmation and a model-checked handoff protocol in M2; reliability targets (zero unauthorized execution, zero replay acceptance) carried into every gate.

## v1.2 (19 October 2026) - engineering revision

v1.2 is an engineering revision over v1.1. Sections [Sec. 9](applications.md#9-domain-applications), [Sec. 10](applications.md#10-application-areas--interoperability), [Sec. 14](roadmap.md#14-success-metrics--gono-go-gates) and [Sec. 15](risks-and-governance.md#15-governance--community) were unchanged except for cross-references; in [Sec. 2](overview.md#2-thesis--positioning) only the comparison table changed (platform on-device models and ZeroClaw, items 4 and 9).

1. **Language decision closed.** Rust-first is confirmed and recorded as [ADR-001](adr/001-core-language.md) with an explicit trigger for revisiting it ([the ADRs](adr)).
2. **`pr3-core` is `no_std + alloc` by construction** and sans-I/O: a `step()` state machine that consumes events and emits actions, with no async runtime, clock, I/O or threads of its own. `std` is an additive Cargo feature, never a separate code path ([Sec. 4.2](architecture.md#42-rust-workspace-host-api-c-abi-and-protocol-client), [Sec. 12](quality-gates.md#12-build-cicd--quality-gates)).
3. **Reach model restated: "PR3 runtime where Rust runs; PR3 protocol everywhere else."** New `pr3-protocol` crate (the stable public contract) and `pr3-client-c` (C11, no dependencies) for consoles, Emscripten/Unreal HTML5, MCU/TEE and other non-Rust hosts ([Sec. 4.2](architecture.md#42-rust-workspace-host-api-c-abi-and-protocol-client), [Sec. 6.4](deployment.md#64-oem--embedded)–6.6).
4. **Inference has three backend classes:** platform models (Apple Foundation Models, Gemini Nano), bundled GGUF via llama.cpp, and the private node. The bundled model download becomes optional; M2 adds a platform-vs-bundled benchmark before committing to a mandatory download ([Sec. 4.3](architecture.md#43-inference-strategy), [Sec. 8.1](benchmarks.md#81-equal-conditions-openjarvis-comparison), [Sec. 11](roadmap.md#11-delivery-roadmap-epics--issues)).
5. **`pr3-llamacpp` reclassified** from "optional adapter" to M1's primary engineering risk, with a concrete binding strategy ([Sec. 4.3](architecture.md#43-inference-strategy), [Sec. 11](roadmap.md#11-delivery-roadmap-epics--issues), [Sec. 13](risks-and-governance.md#13-risks--mitigations)).
6. **Consoles explicitly deferred** with a preserved, cheap path: `no_std` core, C client, and a one-page cognition-tiers RFC ([Sec. 6.7](deployment.md#67-game-consoles---deferred-path-preserved), [RFC-001](rfc/001-console-cognition-tiers.md)).
7. **Mobile, desktop and hybrid confirmed as the product.** The hybrid's role on mobile is restated: the always-on node does the proactive work phones cannot do in the background ([Sec. 6.1](deployment.md#61-fully-offline-mobile)–6.3).
8. **Testing and CI rewritten for Rust:** `#![forbid(unsafe_code)]` enforced in CI, cargo-fuzz on every parser, Miri on core, a no_std check target, a panic-symbol check on the staticlib, and a pinned-emsdk job for the C client ([Sec. 7.2](security.md#72-required-controls), [Sec. 12](quality-gates.md#12-build-cicd--quality-gates)).
9. **ZeroClaw added as a comparable, not a base.** It enters the competitive landscape ([Sec. 2.1](overview.md#21-landscape-and-related-work)), the benchmark program for tool-reliability and security scenarios ([Sec. 8.1](benchmarks.md#81-equal-conditions-openjarvis-comparison)), and the reuse review at the adapter layer ([Sec. 5.1](related-work.md#51-zeroclaw-reuse-candidates-at-the-adapter-layer)). Building PR3 on ZeroClaw was evaluated and rejected ([ADR-001](adr/001-core-language.md), [the ADRs](adr)).
